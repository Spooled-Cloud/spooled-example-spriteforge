Understanding Spooled: A Simple Guide

Don't worry if you're not technical! Here's how this demo works, explained like you're ordering coffee. ☕

📝

What is a Job?

☕ Coffee shop analogy:

A job is like your coffee order slip. It says "make a latte with oat milk" and sits in the queue until a barista picks it up.

📍 In this demo:

When you click "Forge Sprite", we create jobs like "generate frame 1", "generate frame 2", etc. Each is a task waiting to be done.

💻 Example job: 
{
  "queue": "spriteforge-frames",
  "payload": {
    "frame": 3,
    "seed": "pixel-hero",
    "palette": "neon"
  }
}
📋

What is a Queue?

☕ Coffee shop analogy:

The queue is the line of order slips pinned above the espresso machine. First order in = first order made.

📍 In this demo:

We have 3 queues: frames (generate each frame), assemble (combine frames), and public (for scheduled sprites).

💡 Why separate queues?

Different tasks need different handling. Frame generation is quick (many workers), assembly is heavy (fewer workers).

👷

What is a Worker?

☕ Coffee shop analogy:

Workers are the baristas. They grab orders from the queue, make the drinks, and mark orders as complete. More baristas = faster service.

📍 In this demo:

We run 8 frame workers (parallel pixel generation) and 2 assemble workers (combining frames into sprites).

🔄 Scaling:

Busy day? Add more workers. Quiet day? Scale down. Workers pull work automatically—no traffic directing needed.

🔀

What is a Workflow?

☕ Coffee shop analogy:

A workflow is a combo order: "Make coffee A and muffin B, then box them together." Some steps run in parallel (coffee + muffin), some must wait (boxing comes last).

📍 In this demo:

Your sprite workflow: generate all 8 frames in parallel → when ALL done → assemble into final sprite. The "assemble" job depends on all frame jobs.

frame-0 frame-1 ... frame-7 → all done → assemble
🔄

What are Retries?

☕ Coffee shop analogy:

Dropped a drink? Make it again. The order doesn't disappear—it goes back in the queue. Maybe a different barista makes it this time.

📍 In this demo:

The "Chaos" slider simulates failures. At 20%, roughly 1 in 5 frame jobs will "fail" on first attempt. Spooled automatically retries them!

⚙️ Configurable:

You set how many retries (default: 3), delay between retries, and even exponential backoff. Failed 3 times? Mark as permanently failed.

📡

What are Real-time Events?

☕ Coffee shop analogy:

The screen that shows "Order #42 is ready!" That's real-time. You don't keep asking "is my order ready?" — the system tells YOU.

📍 In this demo:

Watch the "Live Events" panel! Every job created, started, completed, or failed appears instantly. The colored dots update in real-time.

🔌 How it works:

Spooled sends events via WebSocket. Our server listens and forwards them to your browser via SSE (Server-Sent Events). Zero polling!

⏰

What are Schedules?

☕ Coffee shop analogy:

The coffee that's automatically brewed at 6 AM every morning, before any customer asks. A scheduled job runs on its own timetable.

📍 In this demo:

"Sprite of the Minute" is a schedule that runs every minute (0 * * * * * cron). It creates a random public sprite automatically.

🕐 Cron examples:

0 9 * * * = daily at 9 AM
0 */2 * * * = every 2 hours
0 0 * * 0 = every Sunday midnight

🔑

How is This Secure?

☕ Coffee shop analogy:

Staff have keys to the back room. Customers don't. The barista uses their key to access supplies, not you.

📍 In this demo:

The Spooled API key stays on our server—your browser never sees it. You talk to our server, our server talks to Spooled. Safe!

Your Browser → Our Server
(has API key) → Spooled Cloud

How Would You Build This With Other Services?

This demo uses jobs, workflows, workers, real-time events, and schedules. Here's an honest look at how you'd implement the same functionality with popular alternatives:

☁️

AWS SQS + Step Functions

How you'd build it:
  • SQS queues for job messages
  • Step Functions for workflow DAG
  • Lambda workers to process jobs
  • API Gateway + WebSocket API for real-time
  • EventBridge for cron schedules
  • DynamoDB to store job state
Trade-offs: Powerful and scalable, but requires orchestrating 6+ services. Step Functions pricing is per state transition. No built-in real-time streaming—you'd build it yourself.
🔴

Redis + BullMQ

How you'd build it:
  • BullMQ queues for jobs
  • Custom code for workflow dependencies
  • Node.js workers with BullMQ
  • Bull Board for monitoring
  • node-cron or BullMQ repeatable jobs
  • Redis Pub/Sub for events (build SSE yourself)
Trade-offs: Great Node.js DX and fast. But you manage Redis infrastructure, implement workflow logic yourself, and build real-time delivery. Data durability depends on Redis persistence config.
⏱️

Temporal

How you'd build it:
  • Temporal workflows for the DAG
  • Activities for frame generation
  • Built-in retries and timeouts
  • Temporal Cloud or self-host cluster
  • Custom real-time layer (Temporal doesn't stream to browsers)
  • Schedules API for cron
Trade-offs: Excellent workflow engine with strong guarantees. However, requires learning their programming model, self-hosting is complex, and there's no built-in browser streaming.
⚡

Inngest

How you'd build it:
  • Inngest functions for each step
  • step.run() for parallel work
  • Built-in retries
  • Cron triggers for schedules
  • Serverless deployment
  • Custom polling/WebSocket for real-time
Trade-offs: Modern DX with TypeScript-first approach. Great for serverless. But event-driven model differs from queue semantics, and you'd build real-time streaming yourself.

🎯 Why We Built Spooled

We wanted a job queue that's simple to start with but powerful enough to scale. Here's what makes Spooled different:

🐘
PostgreSQL as Source of Truth Your jobs live in a real database with ACID transactions. Query them with SQL. No eventual consistency surprises. If Postgres says it's committed, it's committed.
📡
Real-time Built In WebSocket and SSE endpoints are first-class citizens, not afterthoughts. Stream job events to browsers without building a separate pub/sub layer.
🔗
Simple REST API No SDK required. Create jobs with curl. Works with any language. The API is designed to be obvious—if you've used REST, you know Spooled.
🔄
Workflows Without a DSL Define job dependencies with simple JSON. No state machine DSL to learn. Just say "this job depends on those jobs" and we handle the rest.
🏠
Self-Host or Cloud Run on your infrastructure with Docker, or use Spooled Cloud. Same API either way. No vendor lock-in, no data leaving your network if you prefer.
💰
Predictable Pricing Pay per job, not per state transition or message. No surprise bills from chatty workflows. Free tier for experimentation.
🤝 Being honest: Spooled isn't the right choice for everyone. If you need sub-millisecond latency, use Redis directly. If you're all-in on AWS, Step Functions integrates better with Lambda. If you need complex saga patterns, Temporal is more battle-tested.

But if you want a simple, queryable job queue with real-time streaming that you can understand in an afternoon—give Spooled a try.
